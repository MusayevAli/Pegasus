# Booking API v2

The full wire model is `shared/booking-v2.ts`; existing legacy routes remain available. New app routes use `/api/v2` and the configured app Bearer token. Dashboard admin credentials are separate. Backend secrets remain exclusively in `.env` or a server secret manager.

- `GET /providers` reports actual source-specific search/ancillary/seat/quote/checkout/external-booking capabilities. New native clients choose `pegasus_mcp` explicitly; `sample` remains the complete demo flow. `GET /capabilities` retains the sample catalogue and AI status for compatibility.
- `GET /catalog` returns airports, supported pairs, sample date window and fare bundles.
- `POST /ai/search-intent` accepts `{revision,text,context:{currentDate,locale,timeZone},currentIntent}`. It makes a real OpenAI Responses request and returns structured intent, a short summary, model, request ID and latency. Missing key, refusal, invalid output, timeout or cancellation returns `ai_unavailable`; there is no v2 canned AI fallback. Manual search remains available.
- `POST /flights/search` accepts `{intent,provider:"sample"|"pegasus_mcp"}` (omitted provider is legacy sample). Missing departure airport, date, child age, budget scope or baggage scope yields explicit unresolved fields. Valid fields filter the actual sample records; prices include the same confirmed party and supported requested extras. A budget is not silently changed from group to per-person. Different fields produce different cards. Live flexible searches cover at most two destinations and three representative dates (start/middle/end), at most six queries with concurrency two under one overall deadline. Exact single-route/date searches retain their single-query path. Coverage and partial failures are disclosed. Each official continuation matches its particular route/dates; comparison snapshots retain the original search fingerprint.
- `POST /search/alternatives` accepts the same provider selection. Sample mode searches supported nearby-date candidates and calculates exact violated constraints. At most three cards contain real offer IDs, itemised party totals, exact before/after changes and a replacement intent. Locked requirements are preserved. Live mode searches bounded nearby dates (one day before/after the selected date or window) and explicit unlocked budget/timing/connection changes against real returned candidates, with flight-only prices and unverified extras. Outbound-date or date-window locks prevent date expansion. The user must choose a change. An optional real model explanation uses only those candidates; if unavailable, exact deterministic changes remain labelled as such.
- `POST /ai/trip-import` accepts actual image bytes, MIME type, revision and device context. It extracts event or incoming-flight facts, unresolved year/location/time-zone details and an editable planning buffer. Text inside the image is untrusted. Unrelated names, contacts and booking references are excluded. An imported incoming flight is always unconfirmed until the user confirms it. Venue-ground-travel time is unverified, not invented.
- `POST /ai/packing` accepts an actual image and returns item categories, approximate visible counts, uncertainty and request metadata. It does not measure weight/dimensions or assert compliance.
- `POST /ai/compare` accepts two offer IDs, their explicit provider and the same confirmed intent. Mixed-source IDs are rejected. Live comparison uses validated, expiring search snapshots rather than pretending to reprice a held fare. Both sides are recomputed with the same party and needs. Factual price/time/connection/baggage/terms rows remain available if AI explanation fails; no fake explanation is shown. Outbound and return times are formatted in each airport’s IANA time zone, including DST. The AI explanation is qualitative and bounded; numerical facts belong to the recomputed table. The same bag continuing over a connection never becomes additional baggage capacity.
- `GET /offers/:id/services?adults=2&childAges=7` provides products, bundle terms, actual sample seat maps and generated passenger IDs. Extras only apply to eligible Pegasus segments; independently booked flights are never charged again.
- `POST /offers/:id/packing-options` accepts the intent, current selection, confirmed items and measurements per passenger/direction. A photo alone returns `needs_measurements`. Underseat fit requires all three measured axes as well as weight; a linear sum alone is insufficient. Checked baggage compares pieces, total weight, heaviest piece and linear dimensions without pooling. Options preserve seat/meal choices and compare keeping, eligible bags and cheaper bundles against the same needs. Measurements can justify removal of an unnecessary paid bag.
- `POST /quotes` accepts the offer ID, intent, revision and either an explicit selection or null for the cheapest eligible configuration. This is a sample-only operation; live IDs are rejected. The backend calculates every item in integer EUR cents and never charges twice for bundle inclusions. It rejects incompatible dates, trip type, passenger/segment scopes, unavailable/child-ineligible seats, duplicate assignments and unsupported products.
- `POST /checkout` is sample-only and accepts the quote ID, persistent idempotency key, guest traveller names and `paymentMode:demo`. It checks expiry, availability and current price, then stores authoritative status. Optional test outcomes are cancelled/failed. Duplicate attempts return the existing successful demo order. `GET /orders/:id` retrieves it. Names belong only to the required order record, never analytics or AI.

## AI configuration and privacy

Use `OPENAI_MODEL_TEXT` and `OPENAI_MODEL_VISION`, falling back to the existing `OPENAI_MODEL`; the configured default is `gpt-4.1-mini`. The official Responses SDK uses strict Structured Outputs and actual `input_image` content for vision. `store:false` is set. Models cannot create prices, inventory or purchasing operations. Request audits retain only feature, model, provider/request ID, latency, time and validation outcome, not raw search text, photos, names or keys.

The model may interpret explicit requirements and priorities but server schemas/domain checks remain authoritative. Locked current fields must retain their values and remain locked. Clients also compare revisions and cancel superseded requests. Do not replace pending manual edits with stale output.

## Reproducible verification evidence

`backend/evidence/live-search-results.json` records three genuinely executed adult-only synthetic search requests with distinct validated destinations, dates, scope and result IDs. Their successful OpenAI latencies were approximately 4.0, 2.9 and 2.1 seconds. `backend/evidence/live-packing-results.json` records actual analysis of two inspected public object photographs: a packed suitcase produced clothing/bag counts, while a laptop photograph produced one laptop and different uncertainty. The photographs are test inputs, not embedded in deliverable source. These results prove the model path was exercised; they do not prove airline availability.

`live-trip-import-results.json` records actual vision extraction of two locally generated, hash-verified fictional event documents and an incoming-flight fixture. `live-import-search-results.json` applies those confirmed facts: Barcelona on 24 October at 15:00 Europe/Madrid yields one eligible offer with the selected three-hour planning buffer; Berlin on 29 October at 20:30 Europe/Berlin yields two; the independent LGW arrival on 24 October at 08:00 Europe/London yields one eligible onward offer after the connection/check-in buffer. No real travel document was used.

`live-comparison-results.json` records a genuine qualitative comparison and computed alternatives, every alternative re-searched successfully with its exact declared constraint changes. `live-alternatives-results.json` records the final successful, strictly qualitative AI explanations for those exact candidates. `live-insight-results.json` records a valid structured OpenAI insight grounded in synthetic aggregate metric records, including exact evidence IDs and numbers.

The final backend run passed **80 tests**, including live-independent mocked AI validation, scope and pricing rules, retained analytics evidence, no pooling, quote expiry/repricing, incoming connection identity, local-time DST labels and idempotent demo checkout. `npm run build` also passed.

The initial automatic approval review rejected a synthetic child-age test payload; no such request was sent. An initial screenshot upload was also withheld pending proof of contents. A separately reviewed retry was approved after reading the local generator, inspecting the exact synthetic images and verifying their SHA256 manifest; only those verified fixtures were uploaded. Safer explicit adult-only synthetic prompts were approved and used for live evidence. Child-age handling is covered by deterministic and mocked-provider tests.

Provider access and setup limitations are recorded in [PROVIDERS.md](PROVIDERS.md). Test scripts do not call payment or airline fulfilment providers.

## Live provider boundary

See [PROVIDERS.md](PROVIDERS.md) for the real anonymous MCP tool schema and recorded flight results. `FlightOffer` now carries provider/source, official `bookingURL` and capabilities. Unprovided live fields are null: baggage, flight number, bundle, base/extra breakdown, seat availability and fare expiry. Only total provider flight price is shown; ancillary needs remain unverified. Unknown data is never filled from the sample catalogue. Personal travel learning is a separate opt-in capability; see [PERSONALIZATION.md](PERSONALIZATION.md).
